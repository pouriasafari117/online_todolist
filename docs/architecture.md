# معماری و همگام‌سازی

## مرز سیستم

یک وب‌اپ ایستا مستقیماً با GitHub REST API از طریق HTTPS صحبت می‌کند؛ هیچ سرور اختصاصی و هیچ توکنی در کد یا تنظیمات ساخت وجود ندارد. هر کاربر مالک یک مخزن **خصوصی مستقل** برای داده‌های خود است. این مخزن باید پیش از اتصال ساخته شود؛ برنامه مخزن را عمومی نمی‌کند و تغییر تنظیمات دسترسی آن را انجام نمی‌دهد. مخزن کد سایت از مخزن داده جداست. در راه‌اندازی، خصوصی بودن، نام مالک، مخزن، شاخه و مجوزها بررسی و به کاربر نشان داده شوند؛ در صورت عمومی بودن اتصال متوقف شود. خصوصی بودن در هر اتصال مجدد بررسی شود، اما برنامه نمی‌تواند جلوی عمومی شدن بعدی مخزن یا نشت تاریخچه را بگیرد.

برای توکن fine-grained حداقل مجوز عملیاتی مورد انتظار `Contents: read and write` فقط روی مخزن انتخابی است؛ GitHub ممکن است Metadata را به صورت خودکار و فقط خواندنی لحاظ کند. دسترسی به سازمان ممکن است نیاز به تأیید داشته باشد. قابلیت‌ها و پارامترهای رابط GitHub ممکن است تغییر کنند؛ راهنما باید هنگام پیاده‌سازی با مستندات رسمی تأیید شود. هیچ وعده‌ای مبنی بر امکان تنظیم خودکار تمام انتخاب‌های توکن یا ساخت آن با یک کلیک نمی‌دهیم: کاربر باید مالک، مخزن، مجوز، انقضا و تأیید نهایی را در GitHub بررسی و انتخاب کند. اگر محدودسازی یا انتخاب مخزن در رابط موجود نبود، برنامه نباید به توکن گسترده‌تر تنزل خودکار دهد.

فایل پیشنهادی: `data/tasks.json` در شاخهٔ انتخابی مخزن کاربر. فایل جداگانه برای هر حساب در یک مخزن مشترک مرز امنیتی ایجاد نمی‌کند: دسترسی نوشتن Contents به کل محتوای مخزن و تاریخچهٔ آن مربوط است. در این طرح هر مخزن دفتر مستقل خود را دارد. شناسهٔ عددی GitHub برای نمایش و بررسی هویت پایدارتر از نام کاربری است؛ نام می‌تواند تغییر کند.

## مدل دادهٔ پیشنهادی

```json
{
  "schemaVersion": 1,
  "tasks": [
    {
      "id": "8b166d8b-69c5-4bce-8f5b-37e87150a4e9",
      "title": "نمونه کار",
      "description": "",
      "completed": false,
      "priority": "normal",
      "dueDate": null,
      "createdAt": "2026-01-01T12:00:00.000Z",
      "updatedAt": "2026-01-01T12:00:00.000Z"
    }
  ]
}
```

شناسه با `crypto.randomUUID` ساخته می‌شود؛ تاریخ سررسید در صورت استفاده تاریخ تقویمی `YYYY-MM-DD` بدون تبدیل ناخواستهٔ منطقهٔ زمانی است و زمان‌ها UTC هستند. اندازه و تعداد آیتم‌ها و طول فیلدها باید محدود و ورودی‌ها اعتبارسنجی شوند. نسخهٔ ناشناخته یا JSON نامعتبر خطای قابل بازیابی است، نه مجوز بازنویسی. طرح مهاجرت نسخه‌ها باید قبل از تغییر schema نوشته شود. تاریخچهٔ commitها ممکن است نسخه‌های حذف‌شده را نگه دارد.

## پروتکل ذخیره

- بارگذاری با Contents API روی شاخهٔ مشخص؛ محتوای فایل و blob SHA آن مبنای ویرایش است. پاسخ 404 تنها پس از بررسی دسترسی به مخزن و شاخه و تأیید نبود فایل، به معنی دفتر تازه تلقی می‌شود؛ خطاهای دسترسی نباید به ایجاد فایل خالی تبدیل شوند.
- تغییرات ابتدا در حافظهٔ رابط اعمال و به صورت «در انتظار» نمایش داده می‌شوند. نوشتن‌ها در هر دستگاه سریالی و با debounce تجمیع شوند؛ PUT فایل شامل محتوای کامل و SHA آخرین نسخهٔ خوانده‌شده است. برای ایجاد فایل جدید SHA حذف می‌شود. هر موفقیت commit و SHA جدید را ثبت می‌کند.
- روی تعارض SHA یا پاسخ تغییر هم‌زمان، فایل جدید خوانده می‌شود و ادغام سه‌طرفه با نسخهٔ پایه، تغییرات محلی و نسخهٔ دوردست بر اساس شناسهٔ کار انجام می‌شود. تغییرات مستقل قابل ادغام‌اند؛ ویرایش هم‌زمان یک فیلد، حذف در برابر ویرایش و سایر موارد مبهم باید به کاربر نشان داده شوند، نه اینکه با ساعت دستگاه یا آخرین نویسنده بی‌صدا برنده شوند. نتیجه با SHA تازه ارسال می‌شود؛ در تعارض تکراری تلاش محدود و سپس درخواست تصمیم کاربر.
- خطای شبکه، محدودیت نرخ، انقضای توکن، محافظت شاخه و خطای مجوز پیام متمایز دارند. هرگز موفقیت پیش از تأیید GitHub اعلام نشود. پس از پاسخ نامشخص به PUT (مثلاً قطع ارتباط) پیش از تکرار، فایل دوباره خوانده و نتیجه بررسی شود تا commit تکراری یا بازنویسی رخ ندهد.
- تا زمانی که ذخیرهٔ پایدار محلی امن و رفتار بازیابی آن طراحی نشده، تغییرات معلق فقط در حافظه‌اند و با بستن صفحه ممکن است از دست بروند؛ هنگام خروج هشدار داده شود. کار آفلاین پایدار در نسخهٔ اول وعده داده نمی‌شود.

API محدودیت نرخ و اندازه و commitهای پرتعداد دارد؛ تجمیع تغییرات، خطاهای قابل فهم و آزمایش با دو دستگاه لازم است. GitHub تضمین دسترسی همیشگی یا مناسب بودن این الگو برای بار سنگین را نمی‌دهد.

## استقرار

سایت می‌تواند روی GitHub Pages یا میزبان استاتیک HTTPS منتشر شود. ابتدا راهنمای فعال‌سازی و پیکربندی مسیر پایه و شاخه باید با روش استقرار واقعی نوشته و آزمایش شود. API و سایت باید با سیاست امنیت محتوا و بدون وابستگی به localhost کار کنند. انتشار هر تغییر سایت دسترسی به توکن کاربران را تحت تأثیر قرار می‌دهد؛ کنترل انتشار در سند امنیت شرح داده شده است.
